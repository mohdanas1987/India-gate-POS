## PHASE 9A — POS Transaction UX Foundation

### Implemented

Following the CTO's Phase 9A development plan (issued after the conditional-pass audit of commit `120e734`), this pass closed the gaps a fresh inspection of the repo found against that plan's own Phase 9A requirements (category navigation, real product search, cart rebuild, weighted-product entry, keyboard/scanner UX — all working identically online and offline).

**A correctness bug found and fixed before any UI work, because the UI would have exposed it the moment weighted products were used:** `compute_line_total()` (`services/api/app/services/checkout.py`) and its offline mirror (`electron/offlineCheckout.ts`) always computed `unit_price * quantity`, ignoring `is_weighted` — for a weighted product (priced per KILOGRAM, with quantity stored as GRAMS per `OrderLine.quantity`'s own pre-existing docstring), this silently overcharged by 1000x (250g of a €4.00/kg product would have charged €1000.00 instead of €1.00). There was no weighted-product UI yet to have surfaced this, so it was a latent bug, not a regression. Fixed identically in both places: `round(price_minor * grams / 1000)`.

**Category navigation** — new `GET /api/v1/categories` (tenant-scoped, POS-visible product counts per category); `GET /api/v1/products` gained a `category_id` filter param; a new `CategorySidebar` component drives it. Works offline via a new `local_categories` SQLite table, synced alongside the product catalog in the same `catalog:sync` IPC call.

**Real product search** — `GET /api/v1/products`'s search previously matched only name/SKU; it now also matches barcodes (an outer join against `Barcode`, `distinct()`-guarded against a multi-barcode product appearing twice), so a keyboard-wedge barcode scanner's input lands a real hit instead of zero results. The same fix was applied to the offline `searchLocalProducts()`.

**Cart rebuild** — the previous cart was a plain, read-only `<table>` with a single "+1 on click" quantity path and no way to remove a line. The new `CartPanel` component adds: quantity +/- buttons and a direct-entry number field per line (whole-unit products), a per-line Remove button, click-to-select line highlighting, a Clear Cart action, and per-line tax and line-total columns (previously only a price column existed) — all computed with the same weighted-aware math as the backend (`src/lib/pricing.ts`), explicitly documented as a **display-only preview**: the backend independently recomputes and is the sole source of the amount actually charged.

**Weighted-product entry** — a new `WeightEntryDialog` offers the CTO plan's own preset steps (100g/250g/500g/1kg/2kg/5kg/10kg) plus a manual-grams field for anything else, producing only a whole-number-of-grams quantity (never a float), per the plan's explicit "do not store weight as a floating-point money-like value" instruction. No physical scale exists in this environment (`ScaleProvider` remains an unimplemented interface, disclosed since Phase 10 — this dialog is the honest manual-entry path, not a fake scale integration).

**Keyboard/scanner UX** — `F1` focuses the search box; `↑`/`↓` move a keyboard-navigable highlight through the product grid; `Enter` either activates the highlighted product or, if the typed text is an exact match against exactly one visible product's SKU or barcode, adds that product immediately and clears the search — the same outcome a real scanner-then-Enter produces, without inventing an untestable typing-speed heuristic; `Escape` clears the search box. The hotkey bar shows `F3 Hold` / `F4 Recall` **visibly disabled**, labeled "Phase 9B" — not wired to fake functionality.

## PHASE 9B — Customer Attach, Line Discounts (with Approval), Suspended Carts

### Implemented

**Customer attach** — `GET/POST /api/v1/customers` (search by name/phone/email, create), gated on a new `customers.manage` permission; `CustomerPicker.tsx` wires search-or-create into the cart, and `orders.customer_id` records who a sale was for.

**Line-level discounts** — `compute_line_total` (checkout.py) and `computeLineTotal` (pricing.ts) both take a `discount_minor`, clamp it so it can never exceed the line's own subtotal, and compute tax on the discounted base (correct VAT treatment). Cart-level discounts are explicitly out of scope this pass (proportional per-VAT-rate allocation interacts with the Phase 22 X/Z report in a way not safe to rush).

**Discount approval gate** — mirrors the existing refund-approval pattern but runs pre-checkout (`app/services/discounts.py`): a holder of `orders.discount.override` (Store Manager) applies a discount synchronously; a `orders.discount.apply`-only holder (Cashier) over the configured threshold gets a real `Approval` row a manager resolves via the existing `/api/v1/approvals` endpoints, which then completes the sale for the first time on approval. No `ApprovalPolicy` row is seeded for `orders.discount`, so the default is fail-safe: every discount requires approval until a threshold is configured.

**Suspended/held carts** — `POST /api/v1/carts/hold`, `GET /api/v1/carts/held`, `POST /api/v1/carts/held/{id}/recall`. A held cart is a one-shot JSON snapshot (`{product_id, quantity, discount_minor}`); recall deletes the row atomically so the same held cart can't be rung up twice on two terminals. `F3`/`F4` are wired in `PosPage.tsx`; recall re-resolves each line's product via a new `GET /api/v1/products/{id}` since the snapshot doesn't carry full product detail.

## Phase 22.1 — Offline Shift-Start + Sync Hardening (CTO audit of 120e734) — **DONE, this pass's scoped item**

A third CTO-level audit, of commit `120e734` (the Phase 22 work above), was largely positive but named one concrete, testable gap as its clearest remaining architectural hole: *"Device starts offline → cashier wants to open shift → checkout. Not yet supported."* Before this pass, a device that had **never once been online** could not open a cashier session or ring up a sale at all — the disclosed boundary at the end of the Phase 8 rebuild section below ("a device that has never been online cannot start a shift offline") was still true. The CTO's own recommended next gate was a much larger "Phase 9 — Production POS Core"; this pass deliberately scoped down to the one item from that list that is both genuinely offline-architecture work and fully buildable and testable inside this environment — not the full POS UI, Website Orders, multi-store, admin, AI, observability, security certification, GitHub CI, or legacy migration items the same audit also raised (see "Explicitly out of scope" below).

**What was built:**

- **Offline credential caching (`apps/pos/desktop/electron/offlineShift.ts`, new).** The moment an ONLINE login succeeds, the main process now caches a **locally-computed bcrypt hash of the entered password** (`bcryptjs`, pure-JS — no native-module build issues in Electron) via `cacheOfflineCredential()` — never the server's own password hash, never transmitted anywhere, never stored in plaintext. `verifyOfflineLogin()` later checks a login attempt against this cached hash with zero network calls.
- **Register-ownership proof carried offline.** A device may only reopen, while offline, the exact `register_id` it was previously PROVEN (via a real online `resolve_authorized_register()` call that actually succeeded) to be authorized for — cached as `local_known_register` the moment an online session-open succeeds (`main.ts`'s `cash:cache-session` handler). `openShiftOffline()` refuses to open any other register_id, even if the cashier's role would normally permit opening sessions in general — this mirrors the Phase 8.5 "never trust a caller-supplied id" discipline, applied to the offline case where there is no server to ask.
- **Sentinel session pattern.** An offline-opened local session is stored with `session_id: 0` (a placeholder meaning "server hasn't confirmed this yet") and a new `pending_sync: 1` flag. `checkoutOffline()` never actually needed the real server-side session id — only register/store/tenant id — so checkout works identically whether the session is server-confirmed or still pending sync.
- **Outbox ordering guarantee (unchanged code, newly load-bearing).** `OutboxSyncEngine.tick()` already processed queued events strictly `ORDER BY sequence ASC`, one at a time. This pass makes that guarantee do real work: `openShiftOffline()` enqueues a `cash_session.open` event before any `order.created` events from the same shift, so the session always syncs to the server first.
- **Server-side `cash_session.open` handling (`services/api/app/api/v1/sync.py`, new `_process_cash_session_open()`; `services/api/app/services/cash_sessions.py`, new).** Pulled the direct `POST /api/v1/cash/session/open` route's logic into a shared `open_cashier_session()` service — used by BOTH the direct online route and this new sync path — continuing the CTO's repeated "centralize `resolve_authorized_register()` and use it everywhere" theme. It independently re-checks `cash.manage_session` rather than trusting only the route dependency, because the sync endpoint reaches it through `orders.create`, not `cash.manage_session` (the Cashier role holds the former but not a separate sync-admin permission — gating on the latter would break every offline sale's sync). If a session is already open on that register by the time the event arrives (a race, or another device), it is **not** hard-rejected — that would strand every `order.created` event in the same offline batch with nowhere to attach — instead a `Conflict` row is recorded (visible for a human to review) and the existing session is reused, matching the same non-blocking philosophy Phase 8.5 already established for device-sequence gaps.

**What was actually run to verify this, not just written:**

- **Electron/frontend, fully live-verified against real compiled output:** `tsc -p electron/tsconfig.json --noEmit` and `tsc -b --noEmit` both clean; `npm run electron:build` produced fresh `dist-electron/*.js`; a Node script imported that real compiled JS (not TypeScript source, not mocks) against a real SQLite file and proved, in sequence: (A) a device that has never been online is refused with a clear error when it tries to open a shift offline; (B) after simulating one prior successful online login (context + credential + known-register cached, exactly as `main.ts` does it after real HTTP calls), a wrong password is rejected offline and the correct password is accepted using only the cached bcrypt hash; (C) attempting to open a different, unverified register (999) while offline is refused, and no local session is created by the rejected attempt; (D) opening the device's known register (3) offline succeeds, producing a local session with `session_id: 0, pending_sync: 1`; (E) checkout immediately works with zero network calls against that offline-opened session, computing `1210` (2× 500 @ 21% tax) correctly; (F) a second shift cannot be opened while one is already open locally; (G) the outbox contains exactly two events in the correct order — `cash_session.open` at sequence 1, `order.created` at sequence 2.

### Phase 8 rebuild — what "offline-first" now actually means

This is written in detail because it was the audit's central architectural objection, and the standard demanded was reproducible evidence, not a description.

**Server side (`services/api/app/api/v1/sync.py`, new file):** `POST /api/v1/sync/events` accepts a client-generated `event_id` and is idempotent — a replayed event is detected via `InboxEvent`'s unique constraint and returns `already_processed` without reprocessing (proven by `test_sync.py::test_replaying_the_same_event_id_is_idempotent_not_duplicated`, which asserts exactly one `InboxEvent` row and no duplicate order after sending the same event twice). It does **not** trust the client's own computed total: for `order.created` events it recomputes the sale from the server's own product/tax data via the same `create_pos_sale()` the direct checkout API uses, so a compromised or buggy offline client cannot write an arbitrary total to Postgres. A failure partway through (e.g. an unknown product id) is rolled back cleanly and recorded on the `InboxEvent` row (`retry_count`, `last_error`) rather than either silently succeeding or leaving a broken half-written order committed — proven by `test_sync.py::test_a_bad_product_id_is_recorded_as_a_failure_not_a_silent_partial_order`, which explicitly checks no zero-total `OPEN` order exists afterward. An unrecognized `event_type` is rejected with a clear error rather than silently accepted.

**Desktop side, main process (`apps/pos/desktop/electron/main.ts`, `electron/sync/schema.ts`, `electron/offlineCheckout.ts`, all substantially rewritten/new):** on app launch, the local SQLite database is now actually opened and the `OutboxSyncEngine` is actually started — before this fix, neither call existed anywhere, so the outbox and sync engine were, in the audit's own words, "library code, not an operating POS subsystem." The local schema gained `local_products` (id, price, currency, tax rate, barcodes), `local_register_session` (the cached open session), and `local_auth_context` — the pieces the audit correctly identified as missing ("prices aren't locally authoritative, tax isn't locally authoritative, checkout can't validate against the local catalog"). `checkoutOffline()` runs entirely against this local data: it fails loudly (not silently) if there's no cached open session or the product isn't in the local catalog, and otherwise computes the same subtotal/tax/total math as the server (`round(subtotal_minor * rate_basis_points / 10000)`, identical to `Money.percentage()`), writes a local order row, and enqueues an outbox event — all inside a single `better-sqlite3` transaction, so a crash between the two can't happen.

**What was actually run to verify this, not just written:** a Node script drove the real compiled Electron output (`tsc -p electron/tsconfig.json` then imported the resulting JS) against a real SQLite file: checkout before any session was cached failed with a clear error; checkout with a session but an unsynced product failed with a clear error; after seeding a local catalog snapshot, `checkoutOffline` produced `subtotal=2598, tax=546, total=3144` — then a second script ran the actual `OutboxSyncEngine.tick()` against the live API with a real login token, and the event was delivered, marked synced, and produced `GET /api/v1/orders/2` returning the identical `2598 / 546 / 3144` on the server. The offline-computed receipt and the server's authoritative total matched exactly.

**Disclosed boundary, stated plainly rather than hidden (superseded in part by Phase 22.1 above):** at the time of this rebuild, opening or closing a cashier session required connectivity, and a device that had never been online could not start a shift offline at all. **Phase 22.1 (see above) closes the "never been online" case** for a device that has completed at least one prior online login and register-open — it can now open a shift and check out fully offline afterward. A device that has genuinely never once connected still cannot open a shift, and closing a session still requires connectivity either way. Token refresh is still not implemented; if the cached access token expires while the device is offline, sync resumes once the cashier logs in again online. These remain real, current limits, not gaps papered over.
